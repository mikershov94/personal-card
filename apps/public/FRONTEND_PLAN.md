# План развития публичного frontend

## Статус документа

- Статус: согласованный глобальный план.
- Область: только публичное приложение `apps/public`.
- Целевой стек: Next.js 16 App Router, React 19, TypeScript, GraphQL и Feature-Sliced Design.
- Стратегия публикации контента: статический HTML с on-demand ISR.
- Управление контентом: вне frontend, через существующие GraphQL mutations.
- Административный интерфейс, авторизация администратора и frontend CRUD не входят в scope.
- Согласованный UX-референс: [интерактивный прототип](./portfolio-interface-prototype.html).

Прототип фиксирует визуальное направление, композицию, адаптивное поведение и основные состояния.
Демонстрационный контент, inline-стили и скрипты прототипа не являются production-реализацией и не
должны переноситься в приложение без декомпозиции по этому плану.

## Цель продукта

Создать быстрое, доступное и индексируемое персональное портфолио, которое помогает:

- рекрутеру быстро понять специализацию, уровень и релевантный опыт;
- техническому специалисту изучить проекты, стек и ссылки на исходный код;
- потенциальному заказчику или работодателю отправить обращение;
- владельцу обновлять контент через GraphQL без изменения frontend-кода.

Основной пользователь должен получить содержимое портфолио в готовом HTML. Публичные данные не
должны запрашиваться из GraphQL при каждом посещении страницы.

## Границы

### Входит в scope

- одностраничное публичное портфолио;
- адаптивная версия для desktop, tablet и mobile;
- серверное чтение публичного агрегата `getProfile`;
- статическая генерация информационных секций;
- управляемая on-demand ревалидация после изменения данных;
- форма обращения через `createInquiry`;
- SEO metadata, Open Graph, sitemap и robots;
- loading, empty, error и not-found состояния;
- доступность уровня WCAG 2.2 AA как целевая планка;
- frontend-тесты и production-проверки.

### Не входит в scope

- `/admin` и любой другой административный интерфейс;
- login, logout и хранение JWT во frontend;
- формы редактирования профиля, опыта, проектов и навыков;
- просмотр входящих обращений;
- frontend CRUD;
- отдельное frontend-приложение или новый workspace-пакет;
- локальная копия контента, подменяющая данные backend;
- сложная state-management библиотека без подтверждённой необходимости.

## Концепция интерфейса

Выбран формат одностраничного editorial portfolio: спокойная типографика, ясная визуальная
иерархия, много свободного пространства, нейтральный фон и один акцентный цвет. Декоративные
эффекты не должны мешать чтению и навигации.

### Информационная архитектура

1. Header
    - имя или короткий wordmark;
    - якорная навигация по основным секциям;
    - заметный CTA «Связаться»;
    - компактная мобильная навигация.
2. Hero
    - аватар;
    - `displayName`;
    - `headline`;
    - `location`;
    - короткое позиционирование из `summary`;
    - переход к проектам и форме обращения.
3. Skills
    - упорядоченный список `Profile.skills`;
    - компактные теги без искусственных рейтингов и процентов.
4. Experience
    - вертикальная временная шкала;
    - компания, позиция, период, локация и описание;
    - рабочие проекты показываются внутри соответствующего опыта.
5. Personal projects
    - отдельный блок `Profile.projects`;
    - название, описание, технологии, demo URL и repository URL;
    - явное различие между demo и исходным кодом.
6. About
    - расширенный текст профиля, если он не был полностью использован в hero;
    - блок не дублирует содержание hero дословно.
7. Contact
    - имя, email, компания и сообщение;
    - понятные состояния отправки, успеха и ошибки.
8. Footer
    - повтор ключевой навигации;
    - внешние ссылки после появления соответствующего backend-контракта.

### Адаптивность

- Mobile-first базовая разметка.
- На узком экране секции выстраиваются в одну колонку.
- Hero не зависит от фиксированной высоты viewport.
- Timeline опыта остаётся линейным и не требует горизонтального скролла.
- Карточки проектов переходят из сетки в одну колонку.
- Интерактивные элементы имеют достаточную площадь нажатия.
- Текст масштабируется до 200% без потери содержимого и функциональности.

## Пользовательские сценарии

### Основные

1. Посетитель открывает `/` и сразу получает готовое содержимое портфолио в HTML.
2. Посетитель переходит к нужной секции через якорную навигацию.
3. Посетитель изучает навыки, опыт и связанные с опытом проекты.
4. Посетитель отдельно просматривает личные проекты.
5. Посетитель открывает demo или репозиторий проекта во внешнем ресурсе.
6. Посетитель заполняет и отправляет форму обращения.
7. Посетитель получает подтверждение успешной отправки без перезагрузки страницы.

### Ошибки и граничные состояния

- Профиль отсутствует: показывается контролируемое empty state, а не сломанная страница.
- Не заполнена необязательная секция: секция не рендерится и не оставляет пустой отступ.
- Нет опыта или проектов: оставшиеся секции сохраняют логичную композицию.
- GraphQL недоступен во время регенерации: сохраняется последняя успешная статическая версия.
- Некорректно заполнена форма: ошибки связаны с конкретными полями и доступны screen reader.
- `createInquiry` завершился ошибкой: введённые данные не теряются, доступна повторная отправка.
- Внешняя ссылка отсутствует: соответствующее действие не отображается.

## Стратегия рендеринга и кэширования

### Принятое решение

Используется on-demand ISR:

```text
Deploy
  -> getProfile
  -> статический HTML и кэш portfolio

Изменение данных
  -> GraphQL mutation
  -> защищённый POST /api/revalidate/portfolio
  -> инвалидируется кэш portfolio
  -> следующий запрос регенерирует страницу один раз
  -> последующие запросы получают готовую статическую версию
```

### Правила

- Все информационные секции строятся из одного GraphQL query `getProfile`.
- Не выполнять отдельный GraphQL-запрос для каждой секции.
- Загрузчик портфолио работает только на сервере.
- Кэш получает отдельный идентификатор или tag `portfolio`.
- Кэш имеет длительное время жизни; основным механизмом обновления является явная
  on-demand ревалидация.
- Новый deployment создаёт новую статическую версию из актуальных данных.
- После изменения данных без deployment вызывается endpoint ревалидации.
- Endpoint ревалидации не изменяет данные и не является административным UI.
- Механизм должен сохранять последнюю успешно созданную версию при временном отказе API.

### Планируемая реализация Next.js

- Включить `cacheComponents` в `next.config.ts` после отдельной проверки production-сборки.
- Использовать `use cache` на серверном загрузчике или на минимально необходимой серверной
  границе.
- Связать кэш с `cacheTag('portfolio')` либо эквивалентной стабильной политикой Next.js 16.
- Инвалидировать portfolio через серверный Route Handler.
- Не смешивать кэширование публичного чтения с mutation `createInquiry`.
- Проверить фактический результат `next build`: главная страница должна определяться как
  статическая или ISR, а не динамическая на каждый запрос.

Точный API инвалидации (`revalidateTag` или `revalidatePath`) выбирается при реализации после
проверки поведения на установленной версии Next.js. Критерий выбора — один запрос после
инвалидации создаёт новую версию, остальные запросы получают кэш.

### Endpoint ревалидации

Планируемый контракт:

```text
POST /api/revalidate/portfolio
Authorization: Bearer <REVALIDATION_SECRET>
```

Требования:

- принимать только `POST`;
- сравнивать секрет без вывода его значения в логи;
- возвращать `401` при отсутствующем или неверном секрете;
- не принимать имя произвольного path или cache tag от клиента;
- инвалидировать только заранее заданный portfolio cache;
- возвращать короткий машинно-читаемый результат;
- не хранить реальное значение `REVALIDATION_SECRET` в Git;
- добавить только имя переменной в `.env.example`.

### Рабочий процесс обновления контента

1. Выполнить необходимые GraphQL mutations через выбранный внешний клиент или URL.
2. Убедиться, что `getProfile` возвращает обновлённый агрегат.
3. Вызвать `POST /api/revalidate/portfolio` с секретом.
4. Открыть `/` и проверить обновлённую страницу.
5. При ошибке ревалидации не повторять mutation данных: повторить только вызов endpoint.

## Разделение статического и интерактивного UI

### Статическая часть

В статический HTML входят:

- header и навигация;
- hero;
- skills;
- experience timeline;
- рабочие проекты;
- личные проекты;
- about;
- footer;
- разметка формы обращения;
- metadata, Open Graph, robots и sitemap там, где это допускает их контракт.

### Интерактивная часть

Минимальными Client Components остаются:

- мобильное меню, если без клиентского JavaScript нельзя обеспечить выбранное поведение;
- форма обращения и её локальные состояния;
- необязательные небольшие улучшения UX, которые нельзя выразить HTML и CSS.

Интерактивность не должна превращать страницу целиком в Client Component.

### Отправка обращения

Предпочтительный поток:

```text
InquiryForm Client Component
  -> Server Action
  -> createInquiry GraphQL mutation
  -> success или нормализованная ошибка
```

Server Action исключает прямой браузерный запрос к GraphQL и не требует CORS для public frontend.
Она не кэшируется и не вызывает ревалидацию портфолио.

## FSD-архитектура

### Принципы

- `src/app` остаётся специальной директорией Next.js и содержит тонкие route adapters.
- FSD-слой Pages называется `_pages`, чтобы не конфликтовать с Next.js.
- Слой `_app` содержит общеприложенческие стили и реализацию Route Handlers.
- Не создавать слой `widgets` заранее: одностраничные секции сначала принадлежат странице.
- Выносить widget только при появлении самостоятельного крупного блока с повторным
  использованием или собственной сложной композицией.
- Использовать один агрегат `entities/portfolio`, соответствующий публичному read model
  `getProfile`.
- `features/send-inquiry` является единственной пользовательской mutation-фичей первого этапа.
- Каждый slice и значимый segment предоставляет публичный API через `index.ts`.
- Внешний код не импортирует внутренние файлы slice в обход public API.
- Модуль одного slice импортирует другие slice только с нижележащих FSD-слоёв.

## Публичная модель данных

### Источник

Единственный источник информационного содержимого страницы — GraphQL query `getProfile`.

Frontend read model включает:

- профиль: `displayName`, `headline`, `summary`, `location`, `avatarUrl`;
- навыки профиля и их `sortOrder`;
- опыт и его `sortOrder`;
- вложенные проекты опыта;
- личные проекты профиля;
- навыки проектов и их `sortOrder`;
- внешние ссылки проектов.

### Правила преобразования

- Даты API преобразуются в единый presentation format на границе entity.
- `endedAt = null` означает текущее место работы.
- Порядок коллекций принимается из backend-контракта; frontend не переопределяет предметную
  сортировку без явной причины.
- Проекты внутри experience и личные проекты не смешиваются.
- Nullable URL не превращается в неактивную кнопку.
- Некорректный обязательный ответ API считается ошибкой контракта и не маскируется фиктивным
  контентом.

### GraphQL-типы

На начальном этапе допустим небольшой типизированный transport на стандартном `fetch`, чтобы не
добавлять зависимости до отдельного решения. GraphQL Code Generator следует рассмотреть перед
ростом числа операций. Его добавление оформляется отдельным согласованным блоком с объяснением
новых зависимостей.

## Design system

### Токены

Минимальный набор CSS custom properties:

- цвета background, surface, text, muted text, border, accent, success и error;
- типографическая шкала;
- spacing scale;
- border radius;
- container widths;
- focus ring;
- длительности и easing допустимых анимаций.

### Правила компонентов

- Использовать семантические HTML-элементы до создания абстракции.
- Не выносить одноразовую разметку в `shared/ui`.
- Не создавать универсальный компонент с большим количеством режимов ради одной страницы.
- Состояния hover не являются единственным способом показать интерактивность.
- Все focusable элементы имеют видимый `:focus-visible`.
- Анимации учитывают `prefers-reduced-motion`.
- Изображение профиля имеет осмысленный `alt`, размеры и предотвращение layout shift.

## SEO и доступность

### SEO

- корректные `title` и `description`;
- canonical URL;
- Open Graph и Twitter metadata;
- favicon и share image;
- `robots.ts` и `sitemap.ts`;
- один логичный `h1`, последовательная иерархия заголовков;
- внешние ссылки с понятным доступным названием;
- структурированные данные Person/ProfilePage рассматриваются после стабилизации контента.

### Доступность

- landmark-элементы `header`, `nav`, `main`, `section` и `footer`;
- skip link к основному содержимому;
- полная keyboard navigation;
- видимый и контрастный focus;
- контраст текста не ниже WCAG AA;
- программно связанные label и form control;
- сводка ошибок формы и сообщения через подходящий live region;
- отсутствие информации, передаваемой только цветом;
- минимальная область интерактивной цели 24 × 24 CSS px, предпочтительно больше;
- тестирование при zoom 200% и с `prefers-reduced-motion`.

## Инфраструктурные требования

### Environment variables

Планируемые публичные имена без реальных значений:

```text
GRAPHQL_API_URL=
REVALIDATION_SECRET=
NEXT_PUBLIC_SITE_URL=
```

`GRAPHQL_API_URL` и `REVALIDATION_SECRET` доступны только серверному коду. Переменная с префиксом
`NEXT_PUBLIC_` используется только для действительно публичного canonical origin.

### Timeweb

On-demand ISR, Route Handler и Server Action требуют работающий Next.js runtime. Перед реализацией
необходимо подтвердить в Timeweb App Platform:

- для public включена поддержка SSR;
- production запускает `next start` или эквивалентную команду;
- доступны server-side environment variables;
- runtime cache сохраняется в рамках работающего deployment;
- smoke-check обращается к странице после запуска runtime.

Если текущее приложение Timeweb создано без SSR, переход на SSR является отдельным
инфраструктурным решением. Pure static export не является автоматическим fallback: он меняет
контракт формы обращения и процесс обновления контента.

## Тестирование

### Unit tests

- преобразование GraphQL profile в публичный read model;
- форматирование диапазона дат, включая текущее место работы;
- разделение рабочих и личных проектов;
- пропуск секций без данных;
- нормализация GraphQL и network errors;
- проверка авторизации endpoint ревалидации;
- endpoint инвалидирует только portfolio cache;
- validation и состояния формы обращения.

### Component tests

- семантическая структура основных секций;
- проект отображает только существующие внешние ссылки;
- форма сохраняет значения при ошибке;
- успешная отправка имеет доступное подтверждение;
- empty и error states доступны пользователю.

Конкретный test runner выбирается отдельным согласованным блоком, поскольку frontend-тестовых
зависимостей в проекте сейчас нет.

### Browser/e2e scenarios

- главная страница загружается с данными API;
- якорная навигация работает с клавиатуры;
- внешний проект открывается по корректному URL;
- валидная форма создаёт Inquiry;
- невалидная форма показывает ошибки;
- неверный revalidation secret возвращает `401`;
- после mutation и ревалидации страница показывает новое содержимое;
- повторный запрос не вызывает новую загрузку portfolio из GraphQL;
- при ошибке регенерации доступна предыдущая успешная версия.

### Проверки качества

Из корня репозитория:

```shell
pnpm format:check:public
pnpm lint:public
pnpm typecheck:public
pnpm test:public
```

`public-checks` выполняет frontend-тесты, но не запускает production build или runtime smoke-check.
`next build`, запуск через `next start` и on-demand ISR проверяются вручную с реальным GraphQL API
перед deployment.

## Стратегия веток и этапы реализации

### Принципы деления

- Одна feature-ветка представляет законченную пользовательскую возможность, а не технический слой
  FSD.
- Внутри одной ветки может быть несколько последовательных коммит-размерных блоков.
- После каждого блока выполняются релевантные проверки и ревью; переход к следующему блоку требует
  подтверждения пользователя.
- Каждая ветка заканчивается deployable-состоянием и включает необходимые тесты, доступность,
  responsive behavior и документацию своего сценария.
- Не создавать отдельные ветки для `shared`, `entities`, GraphQL transport, SEO или тестов, если они
  не дают самостоятельного законченного результата.
- Не разделять один пользовательский сценарий по техническим слоям.
- Следующую feature-ветку создавать от обновлённого `main` после merge предыдущей.
- Не использовать stacked branches без отдельной практической необходимости.
- Несвязанный рефакторинг не включать в feature-ветку.
- `git add`, `git commit` и `git push` выполняет только пользователь.

Принятая последовательность:

```text
main
 └── feature/public-profile
      └── merge в main
           └── feature/public-experience
                └── merge в main
                     └── feature/public-projects
                          └── merge в main
                               └── feature/public-inquiry
```

UX-прототип и визуальное направление уже согласованы в
[интерактивном прототипе](./portfolio-interface-prototype.html). Реализация начинается с ветки
`feature/public-profile`.

### Ветка 1. `feature/public-profile`

Цель: предоставить небольшое, но законченное публичное портфолио с профилем и навыками, которое
получает данные из GraphQL и обновляется через on-demand ISR.

Коммит-размерные блоки:

1. Frontend foundation
    - создать минимальную FSD-структуру;
    - перенести визуальные решения прототипа в design tokens и global styles;
    - настроить проверяемый server-only env config;
    - создать только необходимые UI primitives;
    - заменить metadata-заглушки.
2. GraphQL profile read model
    - реализовать минимальный GraphQL transport через `fetch`;
    - описать минимальный `getProfile` query для профиля и навыков;
    - типизировать и преобразовать данные в публичную view model;
    - добавить контролируемые contract и network errors;
    - покрыть mapper unit-тестами.
3. On-demand ISR
    - подтвердить SSR-runtime текущего приложения Timeweb;
    - включить и проверить Cache Components;
    - кэшировать публичный read model и присвоить portfolio cache tag;
    - реализовать защищённый endpoint ревалидации;
    - добавить имена environment variables без реальных значений;
    - проверить build-time generation, регенерацию и повторное использование кэша.
4. Profile UI
    - реализовать header, hero, skills, about и footer;
    - добавить якорную навигацию;
    - реализовать responsive, loading, empty и error states;
    - не переносить демонстрационные данные из прототипа в production-код.
5. Готовность сценария
    - заполнить metadata и canonical URL;
    - добавить Open Graph, robots и sitemap;
    - проверить keyboard navigation, focus, contrast, zoom и reduced motion;
    - проверить production build и route classification;
    - описать FSD-границы и безопасный процесс ревалидации.

Результат ветки: `/` показывает статически сгенерированные профиль и навыки, а обновление данных не
требует нового frontend deployment.

### Ветка 2. `feature/public-experience`

Цель: добавить законченный сценарий просмотра опыта без включения UI проектов.

Коммит-размерные блоки:

1. Experience read model
    - расширить `getProfile` полями опыта;
    - типизировать опыт и nullable-поля;
    - реализовать форматирование диапазона дат и текущего места работы;
    - покрыть преобразование и сортировку тестами.
2. Experience UI
    - реализовать timeline опыта;
    - показать компанию, позицию, период, location и description;
    - реализовать отсутствие опыта и nullable-данных;
    - добавить responsive и доступную семантическую структуру.
3. Готовность сценария
    - добавить component/browser tests сценария;
    - проверить ISR с расширенным query;
    - выполнить quality checks и production build;
    - обновить документацию устойчивого codepath.

Результат ветки: посетитель просматривает упорядоченный опыт работы, а страница остаётся статической
между ревалидациями.

### Ветка 3. `feature/public-projects`

Цель: добавить законченный сценарий просмотра рабочих и личных проектов.

Коммит-размерные блоки:

1. Project read model
    - расширить `getProfile` вложенными и личными проектами;
    - типизировать навыки и внешние ссылки проектов;
    - явно разделить рабочие и личные проекты;
    - покрыть преобразование, порядок и nullable URL тестами.
2. Projects UI
    - показывать рабочие проекты внутри соответствующего experience;
    - реализовать отдельную секцию личных проектов;
    - показать project skills;
    - отображать только существующие demo и repository actions;
    - реализовать empty states и responsive layout.
3. Готовность сценария
    - проверить доступные названия внешних ссылок и keyboard navigation;
    - добавить component/browser tests;
    - проверить ISR с полным публичным агрегатом;
    - выполнить quality checks, production build и обновить документацию.

Результат ветки: посетитель различает рабочие и личные проекты и может перейти к доступным внешним
ресурсам.

### Ветка 4. `feature/public-inquiry`

Цель: предоставить независимый интерактивный сценарий отправки обращения.

Коммит-размерные блоки:

1. Inquiry mutation contract
    - описать `createInquiry` operation и типы;
    - синхронизировать frontend validation с backend-контрактом;
    - нормализовать validation, GraphQL и network errors;
    - покрыть contract и error mapping unit-тестами.
2. Inquiry form
    - реализовать `InquiryForm` как минимальный Client Component;
    - добавить Server Action для `createInquiry`;
    - реализовать pending, success и error states;
    - сохранять введённые данные при ошибке;
    - исключить прямой браузерный доступ к GraphQL.
3. Готовность сценария и public frontend
    - проверить labels, error summary, live region и keyboard flow;
    - добавить component/browser tests happy и negative paths;
    - проверить реальный цикл отправки Inquiry;
    - измерить Core Web Vitals и устранить подтверждённые проблемы;
    - выполнить полный public quality gate и Timeweb smoke-check;
    - обновить frontend-документацию и проектный индекс.

Результат ветки: посетитель отправляет обращение с доступной обработкой всех наблюдаемых состояний.

### Последующие изменения

SEO, доступность, responsive behavior, тесты и документация входят в Definition of Done каждой
ветки и не откладываются в общую финальную ветку.

Отдельная ветка создаётся после появления конкретной новой возможности или подтверждённой проблемы,
например:

- `feature/public-profile-links`;
- `feature/public-project-case-studies`;
- `fix/public-keyboard-navigation`;
- `fix/public-isr-revalidation`;
- `fix/public-core-web-vitals`;
- `refactor/public-fsd-boundaries`.

## Backend-возможности для будущих этапов

Текущий публичный контракт достаточен для MVP, но следующие улучшения потребуют отдельных backend
фич:

- ссылки профиля и социальные контакты;
- URL резюме;
- статус доступности к предложениям;
- изображения и обложки проектов;
- highlights и измеримые результаты опыта и проектов;
- отдельные project case studies;
- локализованный контент.

До появления соответствующего контракта frontend не хранит эти данные в фиктивных константах.

## Definition of Done публичного frontend

- `/` отдаёт содержательное статическое HTML-представление портфолио;
- `getProfile` не вызывается при каждом запросе страницы;
- изменение данных становится доступно после защищённой on-demand ревалидации;
- при неуспешной регенерации не теряется последняя рабочая версия;
- страница корректна на mobile, tablet и desktop;
- все обязательные публичные сценарии работают с клавиатуры;
- форма создаёт Inquiry и корректно сообщает об ошибках;
- отсутствующие необязательные данные не ломают композицию;
- metadata, Open Graph, robots и sitemap настроены;
- реальные secrets отсутствуют в репозитории и клиентском bundle;
- format, ESLint, typecheck, frontend tests и production build проходят;
- Timeweb deployment и HTTP smoke-check завершаются успешно;
- архитектурная документация отражает фактическую реализацию.
