# Аутентификация административных GraphQL-мутаций

## Цель

Добавить аутентификацию единственного администратора без пользовательской таблицы в PostgreSQL.
Учётные данные и JWT-конфигурация передаются через переменные окружения. Публичная мутация
`login` выдаёт access token, а управляющие мутации Portfolio требуют валидный Bearer-токен.

## Публичный контракт

```graphql
mutation Login($input: LoginInput!) {
    login(input: $input) {
        accessToken
    }
}
```

Публичными остаются:

- `login`;
- `createInquiry`;
- все GraphQL queries.

Защищаются все управляющие мутации Portfolio:

- создание, изменение и удаление профиля;
- создание, изменение и удаление опыта;
- создание, изменение и удаление проектов;
- создание, изменение и удаление навыков;
- привязка и отвязка навыков от профиля и проектов.

Неверные credentials, отсутствующий, повреждённый или истёкший токен приводят к
`UnauthorizedException`. Ответ при неверных credentials не уточняет, какое именно поле неверно.

## Блок 1. Auth-модуль и выпуск токена

- Согласовать и добавить зависимости для JWT и безопасной проверки хеша пароля.
- Добавить `AuthModule`.
- Описать `LoginInput` и output DTO `AuthPayloadDto`.
- Читать логин администратора, хеш пароля, JWT secret и время жизни токена только из переменных
  окружения.
- Реализовать `AuthService`.
- Покрыть unit-тестами успешный вход, неверные credentials и отсутствие обязательной
  конфигурации.
- Добавить в `.env.example` только имена переменных и безопасные placeholders.

Repository в этом варианте не нужен, поскольку auth-сценарий не использует постоянное хранилище.

## Блок 2. Проверка токена и защита мутаций

- Добавить GraphQL JWT guard.
- Настроить получение HTTP request из GraphQL context.
- Применить guard точечно ко всем административным Portfolio-мутациям.
- Не защищать `login`, `createInquiry` и queries.
- Добавить unit-тесты guard и поведения защищённых resolvers.

Точечная защита выбрана вместо глобального guard: публичная поверхность остаётся явно видна в
resolver-коде, а закрытых операций сейчас меньше.

## Блок 2.5. Публичная login-мутация

- Описать `LoginInput` и `AuthPayloadDto`, если они не потребовались сервисному контракту ранее.
- Реализовать `AuthResolver.login` после сервиса и JWT guard.
- Покрыть resolver unit-тестами успешное делегирование и проброс ошибки сервиса.
- Зарегистрировать resolver последним шагом перед e2e-контрактом.

## Блок 3. E2E-контракт

- Проверить успешный `login`.
- Проверить отказ при неправильном пароле.
- Проверить отказ Portfolio-мутации без токена и с повреждённым токеном.
- Проверить выполнение Portfolio-мутации с валидным токеном.
- Проверить доступность `createInquiry` и публичной query без токена.
- Проверить отклонение истёкшего токена на уровне unit-теста guard либо e2e с тестовым временем
  жизни токена.

## Блок 4. Общая проверка и документация

- Запустить `pnpm pre-commit:check`.
- Запустить `pnpm test:e2e --runInBand`.
- Описать устойчивый auth codepath в `ai-docs/architecture.md`.
- Убедиться, что реальные credentials, хеш пароля и JWT secret не попали в репозиторий.

## Порядок работы

Каждый блок выполняется отдельно. После блока фиксируются результат, изменённые файлы и команда
проверки; переход к следующему блоку выполняется только после пользовательского ревью.
