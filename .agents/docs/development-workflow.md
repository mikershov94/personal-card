# Процесс разработки

## Подготовка задачи

1. Перед изменением изучить релевантный код и текущее состояние репозитория.
2. Кратко сформулировать задачу, затронутые файлы и ограничения.
3. Предложить план. Равноценные решения показать как варианты с плюсами и минусами.
4. Начинать изменение после одобрения плана пользователем.
5. Выполнять работу последовательными коммит-размерными блоками.

В конце каждого блока необходимо указать:

- что сделано;
- какие файлы изменены;
- как проверить результат;
- можно ли переходить к следующему блоку.

Не следует выполнять следующий блок без подтверждения пользователя или реализовывать
несогласованную функциональность на опережение.

## Ветки

- `main` — защищённая стабильная ветка.
- Функциональность разрабатывается в `feature/<scope>`.
- Исправления разрабатываются в `fix/<scope>`.
- Рефакторинг разрабатывается в `refactor/<scope>`.
- Одна ветка соответствует одному законченному предметному изменению.
- Независимо поставляемые части большой области разделяются по веткам, например:
  `feature/portfolio-profile`, `feature/portfolio-experiences`,
  `feature/portfolio-projects`.
- Несвязанный рефакторинг не включается в feature-ветку.

Правила `fix/<scope>` и `refactor/<scope>` являются принятым целевым соглашением, даже если
соответствующие ветки ещё не создавались в истории проекта.

## Коммиты

- Коммит должен представлять один осмысленный и проверяемый блок.
- Предпочтительное деление backend-фичи: схема и миграция, entity/DTO, repository, service,
  resolver/module, e2e.
- Проект после коммита должен собираться либо находиться в явно согласованной TDD-стадии.
- Сообщение коммита кратко описывает результат, а не процесс работы.
- Индексирование, создание коммита и push выполняет только пользователь.
- ИИ-агент никогда не выполняет `git add`, `git commit` или `git push`.

## Pull request и CI

- Изменения попадают в `main` через pull request.
- Перед PR локально запускаются `pnpm pre-commit:check` и e2e-тесты. Для промежуточной проверки
  отдельного приложения используются `pnpm pre-commit:check:api` и
  `pnpm pre-commit:check:public`.
- Merge выполняется только после успешного CI.
- CI запускается для pull request в `main` и push в `main`.
- Служебная job `detect-changes` определяет затронутые области по изменённым путям.
- `api-checks` запускается для изменений API и его e2e/Docker-инфраструктуры, а
  `public-checks` — для изменений public.
- Изменения общих workspace/tooling-файлов и workflow запускают обе проверочные job; изменения
  только документации не запускают проверки приложений.
- Локальная проверка перед PR остаётся полной и не зависит от изменённых путей.
- После merge и production-деплоя проверяются миграции, `/health/live`, `/health/ready` и
  изменённый публичный контракт.

## Production CD

- `cd-api` и `cd-public` запускаются событием `workflow_run` только после успешного push-run
  `ci-pipeline` в `main`; pull request и упавший CI не запускают production job.
- Job `detect-changes` передаёт отдельные production-флаги через artifact
  `deployment-changes`. Docs-only и изменения локального `apps/public/Dockerfile` не требуют
  деплоя.
- API и public используют GitHub Environments `production-api` и `production-public`. В каждом
  environment задаются secret `TIMEWEB_CLOUD_TOKEN` и variables `TIMEWEB_APP_ID`, `HEALTH_URL`.
- API после успешного статуса Timeweb проверяет `/health/live` и `/health/ready`; public выполняет
  HTTP smoke-check `HEALTH_URL`.
- Для ручного повтора используется повтор соответствующей CD job в GitHub Actions. Повтор должен
  сохранить исходный проверенный commit SHA.
- Для rollback в Timeweb запускается новый деплой последнего известного рабочего commit SHA. Перед
  откатом необходимо проверить совместимость уже применённых Prisma migrations.
- Автодеплой в панели Timeweb отключается отдельно для обоих приложений после первого успешного
  управляемого деплоя, чтобы исключить двойной запуск.

Локальная проверка helper не требует токена и не обращается к Timeweb:

```text
node --test .github/scripts/timeweb-deploy.test.mjs
```

Тест покрывает успешный деплой, неуспешный конечный статус, отказ API и timeout. Реальный helper
локально с production credentials не запускается: интеграционная проверка выполняется через CD.

## Рефакторинг

- Рефакторинг не должен менять внешний контракт без отдельного согласования.
- Перед рефакторингом существующее поведение покрывается тестами.
- Исправление, необходимое для текущей фичи, можно выполнить в её ветке.
- Несвязанные улучшения выносятся в `refactor/<scope>`.
- Новая абстракция вводится при наличии текущей потребности, а не только возможного будущего
  использования.
- После рефакторинга выполняется тот же набор проверок, что и после функционального изменения.
