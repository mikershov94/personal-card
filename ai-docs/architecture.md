# Архитектура проекта

## Назначение

Проект — fullstack-приложение в монорепозитории. Основной стек: React, TypeScript,
NestJS, Prisma, PostgreSQL и GraphQL.

## Монорепозиторий

- Пакетный менеджер — pnpm.
- Рабочие пространства описываются в `pnpm-workspace.yaml`.
- Приложения размещаются в `apps/*`.
- Backend находится в `apps/api`.
- Общие команды разработки и CI запускаются из корня репозитория.
- Новые приложения и общие пакеты не создаются без отдельного архитектурного решения.

## Инфраструктура

- Локальные сервисы запускаются через Docker Compose из корня репозитория.
- Development и e2e используют разные конфигурации Compose и разные базы данных.
- Production-образ API собирается корневым `Dockerfile`.
- Перед запуском production API применяются миграции Prisma.
- Public разворачивается в Timeweb как нативное Next.js-приложение; его локальный Dockerfile не
  является production-образом.
- В production используется управляемая PostgreSQL.

## Архитектура public frontend

- `apps/public` следует Feature-Sliced Design; верхний уровень slice делится только на принятые
  FSD-сегменты, например `api`, `model` и `ui`.
- Сетевая логика, GraphQL operations и серверные точки входа к внешнему API размещаются в
  сегменте `api`.
- Если внутри сегмента нужна дополнительная наглядная группировка, используются его подпапки, а
  не новые технические сегменты slice вроде `server`.
- В сегменте `api` публичная точка входа сценария остаётся на верхнем уровне, а детали конкретного
  протокола группируются в семантической подпапке, например `graphql`. Не следует вводить общую
  папку вроде `transport`, если она не выражает самостоятельную архитектурную границу.
- В сегменте `model` центральные предметные типы остаются на верхнем уровне, а связанная логика и
  её тесты группируются в семантические подпапки, например `mapping`. Не следует создавать общую
  папку `types`, пока она не выражает самостоятельную границу и содержит только один файл.
- Серверные загрузчики профиля и конфигурация с секретами помечаются импортом `server-only`,
  вызываются только из серверного Next.js codepath и не импортируются Client Components.
  Отдельные `index.server.ts` для этого не используются.
- Ответ внешнего GraphQL API сначала рассматривается как `unknown`; обязательные поля проверяются
  до создания frontend read model.
- Frontend сохраняет предметный порядок коллекций из backend и не подставляет фиктивный контент
  при ошибке контракта.
- Network, HTTP, GraphQL, not-found и contract errors различаются. Not-found определяется по
  структурному статусу в `errors.extensions`, а не по локализованному тексту сообщения.
- Универсальные GraphQL response contracts, guards, predicates и протокольная механика запроса
  размещаются в `shared/api/graphql`; предметные query, интерпретация ответа и error mapping
  остаются внутри `api` соответствующего slice. Общий GraphQL request helper может
  инкапсулировать POST-запрос, обработку network/HTTP сбоев, чтение JSON и проверку response
  envelope, но получает фабрики предметных ошибок от вызывающего slice и не зависит от его типов.
  Универсальные TypeScript guards размещаются в `shared/lib/typeguards`.
- Frontend environment variables декларативно валидируются через `@t3-oss/env-nextjs` и Zod.
  Значения `process.env` перечисляются явно в `runtimeEnv`; дополнительная проектная обёртка над
  `createEnv` не вводится без собственной логики.
- Новая runtime-библиотека не добавляется только ради TypeScript-типов, если проект не использует
  её поведение. В частности, серверный GraphQL read path остаётся на стандартном `fetch` и не
  зависит от Apollo Client.
- Секреты и реальные значения переменных окружения не сохраняются в Git.

### Production-деплой

Production CD разделён по приложениям и запускается только после успешного push-run
`ci-pipeline` в `main`:

```text
push main -> ci-pipeline -> deployment-changes artifact
                            ├── cd-api -> Timeweb API -> live/ready checks
                            └── cd-public -> Timeweb API -> HTTP smoke-check
```

CI сохраняет deploy-флаги и SHA проверенного коммита в короткоживущем artifact. CD повторно
проверяет SHA artifact против исходного CI run и передаёт этот commit SHA в Timeweb. Каждый
workflow ожидает конечный статус конкретного созданного деплоя; параллельные деплои одного
приложения запрещены отдельной concurrency group.

API продолжает собираться Timeweb из корневого `Dockerfile`, а Prisma migrations выполняются
`docker/api-entrypoint.sh` перед запуском приложения. GitHub Actions не получает доступ к
production PostgreSQL.

Production-конфигурация хранится в GitHub Environments `production-api` и `production-public`:

- secret `TIMEWEB_CLOUD_TOKEN` — токен Timeweb Cloud API;
- variable `TIMEWEB_APP_ID` — ID соответствующего приложения;
- variable `HEALTH_URL` — базовый URL API или полный URL public-приложения.

Реальные значения не документируются и не сохраняются в репозитории. Откат выполняется новым
деплоем последнего известного рабочего commit SHA через Timeweb; миграции при этом должны оставаться
обратно совместимыми. Встроенный автодеплой Timeweb отключается только после первого успешного
деплоя через GitHub CD.

## Архитектура backend

Backend организован по предметным NestJS-модулям. Небольшой модуль может использовать один
resolver, а модуль с несколькими GraphQL entity разделяет resolvers внутри общей предметной
границы:

```text
feature/
├── dto/
├── entities/
├── repositories/
├── resolvers/
│   ├── first.resolver.ts
│   ├── first.resolver.spec.ts
│   ├── second.resolver.ts
│   └── second.resolver.spec.ts
├── services/
│   ├── first.service.ts
│   ├── first.service.spec.ts
│   ├── second.service.ts
│   └── second.service.spec.ts
└── feature.module.ts
```

Несколько resolvers одного агрегата не требуют отдельных NestJS-модулей. Общий модуль сохраняется,
пока сценарии используют одну предметную границу. Если общий service становится слишком широким,
его можно разделить на профильные application services внутри того же модуля без создания новых
NestJS-модулей.

Основной поток зависимостей:

```text
GraphQL Resolver -> Application Service -> Repository -> PrismaService -> PostgreSQL
```

### Ответственность слоёв

- Resolver описывает GraphQL-контракт, принимает аргументы и делегирует сценарий сервису.
- Resolver не обращается к Prisma или repository напрямую.
- Service реализует сценарий использования и не зависит от GraphQL-транспорта.
- Repository инкапсулирует Prisma-запросы и детали хранения данных.
- Repository дополняет клиентские данные persistence-only полями и значениями по умолчанию,
  которые не должны задаваться GraphQL-клиентом.
- `PrismaService` является общей инфраструктурной зависимостью доступа к PostgreSQL.
- Entity описывает GraphQL output-тип.
- Input DTO описывает GraphQL input и декларативную валидацию.
- NestJS-модуль явно импортирует инфраструктурные модули и регистрирует свои providers.

### Prisma

- Prisma-модели разделяются по предметным файлам в `apps/api/prisma/models`.
- Миграции являются частью исходного кода и проходят ревью вместе с изменением модели.
- Изменение Prisma-модели и соответствующая миграция составляют один согласованный блок.
- Prisma Client генерируется после изменения схемы и перед проверкой типов или сборкой.

### Development-фикстуры и seed-скрипты

- Development-фикстуры не относятся к production-коду предметных модулей и размещаются в
  `apps/api/fixtures/<domain>`.
- Типы фикстур и сами данные хранятся в отдельных файлах.
- Исполняемая логика заполнения БД размещается в `apps/api/scripts`, отдельно от данных и `src`.
- Seed entrypoint регистрируется через `migrations.seed` в `apps/api/prisma.config.ts` и
  запускается канонической командой Prisma `prisma db seed`.
- Детерминированный Portfolio seed заменяет только локальные Portfolio-данные в одной транзакции;
  его нельзя направлять на e2e или production-базу.

### Практические ограничения

- Для небольшого проекта используются конкретные repository-классы.
- Абстрактный repository или интерфейс вводится при появлении второй реализации либо реальной
  точки вариативности, а не заранее.
- Ошибка отсутствия сущности преобразуется в осмысленное NestJS-исключение на уровне,
  располагающем нужным контекстом.
- Все GraphQL-операции имеют явный возвращаемый тип.
- Для успешного удаления GraphQL mutation возвращает `Boolean`, поскольку GraphQL не имеет
  типа `void`.

## Предметная модель Portfolio

Portfolio использует нормализованную модель, в которой профиль является корнем публичного чтения:

```text
Profile
├── Experience
│   └── Project
├── Project (личный, без Experience)
├── ProfileLink
└── ProfileSkill ─── Skill
                    ├── ExperienceSkill
                    └── ProjectSkill
```

Основные связи:

- `Profile 1 -> N Experience`;
- `Profile 1 -> N Project`;
- `Experience 1 -> N Project`;
- связь `Project -> Experience` необязательна, чтобы поддерживать личные проекты;
- `Profile`, `Experience` и `Project` связываются со справочником `Skill` через отдельные
  join-модели.

Вложенные коллекции загружаются repository корневой сущности. Repository явно задаёт их
детерминированную сортировку, включая дополнительные критерии при одинаковом `sortOrder`.
GraphQL entity отражает загруженные отношения, а unit- и e2e-тесты проверяют порядок элементов.

### Реализованный codepath навыков

`Skill` является справочником с уникальным регистрозависимым полем `name`. Категории навыков пока
не моделируются. `ProfileSkill` связывает навык с singleton-профилем, хранит `sortOrder` и удаляется
каскадно при удалении профиля или навыка.

`SkillResolver` предоставляет создание, обновление и удаление навыков, а также их привязку и
отвязку от профиля. `SkillService` перед созданием связи проверяет существование профиля и
навыка. `ProfileRepository` загружает связи вместе с `Skill` и сортирует их по `sortOrder`, затем по
`skillId` как устойчивому tie-breaker. GraphQL-профиль возвращает связь, содержащую `skill` и
`sortOrder`, а не плоский массив навыков.

### Реализованный codepath проектов

`Project` принадлежит singleton-профилю и может быть личным (`experienceId = null`) или связанным с
конкретной записью опыта того же профиля. При удалении `Experience` связанные проекты удаляются
каскадно. `profileId` является внутренним persistence-полем и не раскрывается через GraphQL.

`ProjectResolver` предоставляет создание, обновление и удаление проектов через `ProjectService`.
Service проверяет существование профиля и, при необходимости, связанного опыта, а
`ProjectRepository` инкапсулирует Prisma-запросы и предметные ошибки. Частичное обновление
поддерживает три состояния `experienceId`: отсутствие поля не меняет связь, `null` делает проект
личным, UUID привязывает проект к существующему опыту.

`SkillResolver` также предоставляет привязку и отвязку навыков к проекту. Сценарий проходит через
`SkillService`, который проверяет существование проекта и навыка, а `SkillRepository` управляет
join-моделью `ProjectSkill`. Вложенное публичное чтение выполняется через `getProfile`:
`Profile.projects` содержит только личные проекты, `Profile.experiences[].projects` — проекты
соответствующего опыта. Проекты сортируются по `sortOrder`, затем `title`, затем `id`; навыки
проекта сортируются по `sortOrder`, затем `skillId`.

Достижения, которыми нужно независимо управлять через API, моделируются отдельными сущностями
вроде `ExperienceHighlight` и `ProjectHighlight`, а не массивами строк.

Изменения Portfolio поставляются вертикальными бизнес-возможностями:

```text
Prisma -> Repository -> Service -> Resolver -> unit tests -> e2e tests
```

Не следует делить ветки по техническим слоям, поскольку промежуточная ветка не предоставляет
законченного публичного сценария.

## Аутентификация административных мутаций

Приложение использует учётные данные единственного администратора без пользовательской таблицы.
Логин администратора, Argon2-хеш пароля, JWT secret и срок действия access token поступают только
из переменных окружения. Реальные credentials и секреты не сохраняются в репозитории.

Публичный auth codepath:

```text
GraphQL login -> AuthResolver -> AuthService -> Argon2 verify -> JwtService sign
```

`login`, `createInquiry` и все GraphQL queries доступны без токена. Управляющие Portfolio-мутации
защищаются точечным `JwtAuthGuard`. Guard получает HTTP request из GraphQL context, извлекает строго
`Bearer <token>` и проверяет подпись и срок действия через `JwtService`. Отсутствующий,
повреждённый или истёкший токен приводит к GraphQL-ошибке с единым публичным сообщением, машинным
кодом `UNAUTHENTICATED` и HTTP-статусом `401 Unauthorized`. Чтобы Apollo не сбрасывал статус ошибки
выполнения операции на `200`, GraphQL-модуль использует
`preserveHttpStatusForExecutionErrors: false`.

Auth-модуль не использует repository и Prisma: постоянное хранение в этом сценарии отсутствует.
GraphQL input и output оформляются DTO, поскольку auth payload не является хранимой предметной
сущностью.

### Миграции в feature-ветках

Миграцию текущей feature-ветки можно пересоздать до merge, если в ходе реализации исправляется
контракт той же фичи и пользователь явно подтвердил пересоздание. Существующие Git-коммиты при этом
можно сохранить: чистой должна быть итоговая Prisma-история ветки, а переписывание Git-истории —
отдельное решение. Если старая миграция применялась только в локальной disposable-базе, базу можно
сбросить и воспроизвести миграции заново.

Миграцию нельзя переписывать после merge, release или применения в общей среде. Такие изменения
оформляются новой корректирующей миграцией с сохранением данных и совместимости истории.

## Открытые архитектурные решения

Следующие вопросы пока не являются правилами проекта:

- mapper-классы между Prisma-моделями и GraphQL entities;
- создание общих workspace-пакетов;
- обязательный CRUD для каждого предметного модуля.
