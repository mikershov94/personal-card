# Подход к тестированию

## Общие правила

- Предпочтительный процесс — TDD: сначала описываются типы, сигнатуры и контракт объектов и
  функций, затем пишется тест, который падает по ожидаемой причине, после чего добавляется
  минимальная реализация и выполняется рефакторинг на зелёных тестах.
- Названия `describe` и `it` пишутся на русском языке.
- Для каждого публичного сценария предусматривается минимум один happy path и один
  осмысленный negative path.
- Негативный тест должен проверять реальную границу или ошибку, а не искусственное исключение.
- Тесты проверяют наблюдаемое поведение и взаимодействие слоёв, а не внутренние детали метода.
- Тестовые данные не должны содержать production-секреты или зависеть от production-сервисов.

## Unit-тесты

Каждый слой тестируется изолированно:

- resolver использует mock сервиса;
- service использует mock repository;
- repository использует mock `PrismaService`;
- инфраструктурный сервис использует mock своих внешних зависимостей.

Unit-тесты проверяют:

- возвращаемое значение или выброшенную ошибку;
- вызов следующего слоя с ожидаемыми аргументами;
- отсутствие нежелательного вызова в негативном сценарии, когда это важно.

Repository преобразует распознанные ошибки persistence-слоя в конкретные NestJS-исключения с
предметным сообщением: например, отсутствие сущности — в `NotFoundException`, конфликт
уникальности — в `ConflictException`. Неизвестная инфраструктурная ошибка не раскрывается наружу
и преобразуется в `InternalServerErrorException`. Repository unit-тест имитирует исходное условие
Prisma и проверяет точные тип и сообщение публичного исключения; generic `Error` не используется
как ожидаемый результат repository.

Повторяющееся преобразование Prisma-ошибок выполняется через общий
`src/prisma/helpers/prisma-error.helper.ts`. Соответствия Prisma-кодов, типов NestJS-исключений и
сообщений хранятся в предметных config-файлах рядом с repository. Config остаётся предметным: не
следует объединять сообщения разных модулей в один глобальный набор. Unit-тест mapper проверяет
выбор известного кода и fallback, а repository spec сохраняет проверку конкретного публичного
исключения для каждого сценария.

Тестируемый класс следует создавать через NestJS TestingModule, если тесту важна корректность
регистрации зависимостей. Простое прямое создание допустимо для полностью изолированного
класса без NestJS DI.

## E2E-тесты

- E2E обращается к приложению через настоящий HTTP/GraphQL endpoint.
- Используется отдельная PostgreSQL, запускаемая через `compose.e2e.yaml`.
- Перед тестами применяются настоящие миграции Prisma.
- E2E проверяет GraphQL-ответ и, когда это существенно, фактическое состояние PostgreSQL.
- Данные очищаются между сценариями, чтобы тесты не зависели от порядка выполнения.
- Development и production базы данных никогда не используются для e2e.
- Подъём БД, миграции, тесты и освобождение ресурсов выполняются одной корневой командой.

## Уровни проверки

Быстрая локальная проверка:

```shell
pnpm test
```

Полная e2e-проверка:

```shell
pnpm test:e2e --runInBand
```

Проверка перед коммитом:

```shell
pnpm pre-commit:check
pnpm test:e2e --runInBand
```

CI выполняет проверки только для затронутых приложений:

- `api-checks` генерирует Prisma Client, проверяет форматирование, ESLint и типы API, запускает
  unit- и e2e-тесты, затем выполняет API production build;
- `public-checks` проверяет форматирование, ESLint и типы public, затем выполняет public
  production build через `next build`; frontend-тестов в этой job нет;
- при изменении общих workspace/tooling-файлов запускаются обе job;
- изменение только документации не запускает проверки приложений.

Локальные полные команды сохраняют проверку всего монорепозитория: `pnpm pre-commit:check`
охватывает оба приложения, а API e2e отдельно запускаются через `pnpm test:e2e --runInBand`.

## Пока не зафиксировано

- обязательный процент покрытия;
- обязательные интеграционные тесты между unit и e2e;
- единая фабрика тестовых данных для всех модулей.
