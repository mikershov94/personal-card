# Правила проекта

## Контекст

- Проект — fullstack-приложение в pnpm-монорепозитории.
- Стек: React, TypeScript, NestJS, Prisma, PostgreSQL и GraphQL.
- Backend находится в `apps/api`. Новые приложения и workspace-пакеты создаются только после
  согласования архитектуры.
- Секреты и реальные значения переменных окружения запрещено сохранять в репозитории.

## Обязательный порядок работы

1. Перед предложением решения изучить релевантный код и текущее состояние репозитория.
2. Кратко сформулировать задачу, ограничения и затронутые места.
3. Предложить план. При наличии равноценных решений показать варианты и дождаться выбора.
4. Не изменять код до одобрения плана пользователем.
5. Выполнять работу по одному коммит-размерному блоку.
6. В конце блока перечислить результат, изменённые файлы и способ проверки, затем остановиться
   до команды пользователя.
7. Не добавлять зависимости и не принимать новые архитектурные решения без объяснения и
   согласования.
8. Никогда не выполнять `git add`, `git commit` и `git push`: это делает только пользователь.

## Архитектурные границы backend

- Основной поток зависимостей:
  `GraphQL Resolver -> Service -> Repository -> PrismaService -> PostgreSQL`.
- Resolver не содержит бизнес-логику и не обращается к Prisma напрямую.
- Service реализует сценарий использования и не зависит от GraphQL-транспорта.
- Repository инкапсулирует Prisma-запросы.
- Entity описывает GraphQL output, input DTO — GraphQL input и его валидацию.
- Не вводить абстракции, mapper-классы и инфраструктуру «на будущее» без текущей потребности.

## Качество и тестирование

- Предпочтительный подход — TDD: падающий тест, минимальная реализация, рефакторинг на зелёных
  тестах.
- Названия `describe` и `it` пишутся на русском языке.
- Для публичного сценария нужен минимум один happy path и один осмысленный negative path.
- Unit-тесты изолируют текущий слой; e2e проходят через HTTP/GraphQL и отдельную PostgreSQL.
- Перед PR должны проходить форматирование, ESLint, typecheck, unit-тесты, e2e и build.

## Ветки и изменения

- Фичи: `feature/<scope>`.
- Исправления: `fix/<scope>`.
- Рефакторинг: `refactor/<scope>`.
- Одна ветка и один коммит-размерный блок должны представлять одно осмысленное изменение.
- Несвязанный рефакторинг не включать в feature-ветку.
